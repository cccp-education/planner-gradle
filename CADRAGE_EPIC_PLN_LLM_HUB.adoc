== Vision

Planner consomme codebase (N1) comme socle LLM unifié — remplacement
du `OllamaBridge` standalone (singleton, instance unique, zéro pool)
par le pattern `LlmBuildService` prouvé sur slider (SLD-8 US-8.1/8.2)
et capsule (CAP-ARCH-1). Planner devient le 3e consommateur d'un hub
N1 standardisé, gagnant pool rotation 11437-11465 + quota failover +
cycling multi-modèles gratuitement.

== Audit — 6 constats

[cols="1,3,3", options="header"]
|===
| # | Constat | Preuve

| 1
| Planner a un bridge LLM standalone minimaliste
| `planner-plugin/.../OllamaBridge.kt:1-24` — object singleton 24 lignes, `OllamaChatModel.builder()` direct, instance unique `localhost:11437`. Zéro pool, zéro failover, zéro rotation.

| 2
| Le port est hardcoded 11437 (extrême de la plage autorisée)
| `OllamaBridge.kt:9` (`DEFAULT_BASE_URL = "http://localhost:11437"`), `PlanningPlugin.kt:11`, `IntentionPlanner.kt:24,42,59`. Si 11437 tombe, le build échoue — pas de rotation vers 11438-11465.

| 3
| Le modèle est hardcoded `gemma4:31b-cloud` (un seul)
| `OllamaBridge.kt:10` (`DEFAULT_MODEL_NAME = "gemma4:31b-cloud"`), 4 sites au total. codebase cycle `gpt-oss:120b-cloud` + `gemma4:31b-cloud` (OllamaInstanceFactory.AUTHORIZED_MODELS). Planner ne bénéficie pas du cycling.

| 4
| 3 surcharges `IntentionPlanner.plan()` construisent un ChatModel interne
| `IntentionPlanner.kt:26,44,62` — chacune appelle `OllamaBridge.chatModel(ollamaModel, ollamaBaseUrl)`. Le ChatModel n'est pas injectable — la testabilité requiert un mock HTTP via `-Pollama.baseUrl`.

| 5
| `DecomposeIntentionTask` passe 2 propriétés string (model/baseUrl)
| `DecomposeIntentionTask.kt:32-35` — `ollamaModel: Property<String>`, `ollamaBaseUrl: Property<String>`. Pas de `@ServiceReference` vers un BuildService. Pattern pré-SLD-8.

| 6
| slider + capsule ont déjà migré, planner est le dernier holdout
| `slider-plugin/.../AssistantManager.kt:75-113` + `capsule-plugin/.../CapsuleLlmService.kt:63-97` — pattern identique `registerLlmBuildService()` + `resolveModel()` + `LlmProviderChatModelAdapter`. Planner est le seul borough N2 actif encore en OllamaBridge standalone.
|===

== Décisions architecturales

. *Portée EPIC* : remplacer `OllamaBridge` (standalone) par consommation
  de `codebase.koog.llm.service.LlmBuildService` (N1 hub). Planner gagne
  pool round-robin 11437-11465 + quota failover + cycling 2 modèles.
  Zéro bump BOM — `codebase-plugin` 0.0.5 déjà publié Central.

. *Pattern consommateur* : mirror strict de `CapsuleLlmService.kt`
  (template le plus propre, 113 lignes, sans legacy factories). Nouveau
  `PlanningLlmService` (object, domaine `planning.llm`) + nouveau
  `LlmProviderChatModelAdapter` (copy slider/capsule, 49 lignes).

. *Backward compat mock-LLM* : quand `-Pollama.baseUrl` est set (tests
  GradleTestKit/Cucumber), fallback sur `OllamaChatModel` pointant vers
  le mock HTTP (pattern slider/capsule). En production (pas de
  `-Pollama.baseUrl`), `LlmBuildService` résout le provider depuis le pool.

. *Injection ChatModel* : `IntentionPlanner.plan()` accepte un
  `ChatModel` paramètre au lieu de construire `OllamaBridge.chatModel()`
  interne. Les 3 surcharges actuelles fusionnent vers 2 : une avec
  `Logger` Gradle, une avec SLF4J (tests unit). Le ChatModel est résolu
  par `PlanningLlmService.resolveModel()` dans `DecomposeIntentionTask`.

. *Suppression `OllamaBridge.kt`* : 24 lignes supprimées. Les 2 tests
  `OllamaBridgeTest` (null-check triviaux) supprimés — remplacés par
  tests `PlanningLlmServiceTest` (registration, resolution, mock fallback).

. *Suppression propriétés `ollamaModel`/`ollamaBaseUrl`* de
  `DecomposeIntentionTask` et `PlannerExtension` — remplacées par
  `@ServiceReference LlmBuildService` + propriété `aiProvider`
  (`-Pai.provider`, défaut `"ollama"`).

. *Dépendance Gradle* : `implementation(libs.codebase.plugin)` ajouté
  à `planner-plugin/build.gradle.kts`. codebase-plugin 0.0.5 déjà
  publié Central. Pas de bump BOM racine (codebase n'est pas dans la
  BOM — c'est un plugin N1 consommé directement).

. *Non-régression critique* : `PlannerIntegration.kt` (codebase) appelle
  `IntentionPlanner.plan(eagerContext, ragContext, ...)`. Le contrat
  d'appel (4 String + Logger → Plan) est préservé. Seul le résolveur
  ChatModel change (pool au lieu de singleton).

. *Méthode* : baby-step DDD/TDD/BDD, 3 niveaux tests/US
  (unit → functional → cucumber), English only code/Gherkin.

. *Ordre* : US-1 (PlanningLlmService + adapter, indépendant) →
  US-2 (wiring + suppression OllamaBridge) → US-3 (Cucumber BDD).

== Risques et mitigations

[cols="2,3,3", options="header"]
|===
| Risque | Impact | Mitigation

| Poids transitiif codebase-plugin (RAG + pgvector + koog)
| Build time planner augmente
| slider + capsule payent déjà ce coût sans issue. codebase-plugin 0.0.5 est un JAR publié, résolu depuis Maven Central (pas recompilé).

| `PlannerIntegration.kt` (codebase) appelle `IntentionPlanner.plan()`
| Si signature change, codebase casse
| Signature préservée — `plan(intention, context, specContents, eagerContext, ragContext, graphifyContext, docsContext, logger, ChatModel)` — ChatModel injecté au lieu de construit interne. Backward compat : 2 surcharges (avec/without multi-channel).

| Tests Cucumber existants (`planner_vibecoding.feature`, `planner_verify.feature`, `planner_budget.feature`)
| Si mock-LLM fallback casse
| Pattern slider/capsule prouvé : `-Pollama.baseUrl` détecté → `OllamaChatModel` mock, pas de pool. Cucumber scenarios inchangés.

| `OllamaBridgeTest` supprimé
| Couverture diminue
| Remplacé par `PlanningLlmServiceTest` (registration, resolution, mock fallback) — couverture supérieure (10 tests vs 2 null-check).
|===
