=== GREEN — `PlannerVerifySteps` + shared state

Création `PlannerVerifySteps.kt` (pattern `PlannerVibecodingSteps`,
`En` java8, AssertJ). Problème : les steps `Given an intention {string}`,
`When the response is parsed into a Plan`, `When the planner builds its
prompt`, `Then the plan should contain {int} task(s)` sont déjà définis
dans `PlannerVibecodingSteps` → `DuplicateStepDefinitionException`
(Cucumber refuse les duplications à travers classes du glue path).

Solution : introduire un **shared scenario state** ("World" pattern
Cucumber) :

. `PlannerScenarioState.kt` — `object` Kotlin singleton avec les 5 champs
  mutables (`rawJson`, `parsedPlan`, `parsingException`, `prompt`,
  `stdout`) + `reset()`.
. `PlannerScenarioStateReset.kt` — `object` avec `@Before @JvmStatic`
  hook Cucumber pour reset par scénario (le singleton otherwise
  fuiterait l'état entre scénarios).
. `PlannerVibecodingSteps` refactoré : champs d'instance supprimés,
  imports `planning.steps.PlannerScenarioState.*` ajoutés (5 champs
  lus/écrits via le singleton).
. `PlannerVerifySteps` : step definitions verify-specifics uniquement
  (les steps partagés sont delegués à `PlannerVibecodingSteps` — les
  deux classes accèdent au même état partagé).

Bug compilation : `assertThat(prompt).contains("x", ignoreCase = true)`
invalide sur `AbstractStringAssert<*>` (AssertJ) — l'overload
`ignoreCase` n'existe pas. Fix : `prompt.lowercase().contains("x")`
(2 sites affectés : les steps `expectedOutput required` et `verifyHook
optional rare`).

== Décisions architecturales

. *Shared state pattern* — Cucumber java8 instantiate chaque step class
  indépendamment, les champs d'instance ne sont PAS partagés entre
  classes. Le pattern "World" (singleton + `@Before` reset) est la
  solution standard pour partager l'état entre step classes du même
  glue path.
. *Pas de runner dédié* — `CucumberTestRunner` existant découvre toutes
  les features du classpath `features/`, pas besoin d'un runner
  séparé pour `planner_verify.feature` (pattern S-061
  `planner_contracts.feature` qui réutilisait déjà le runner).
. *Zéro production modifié* — baby-step BDD pur. Les US-1/2/3 ont
  étendu le code de production (BOM 0.0.3 + planner + codebase bridge),
  l'US-4 documente que le contrat est tenu end-to-end via Cucumber.
