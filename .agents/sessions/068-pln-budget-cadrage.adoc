=== Constat 2 — ChannelBudget tronque avec proportions fixes

=== Constat 5 — Le split-brain est fixe-vs-dynamique, pas dumb-vs-smart

`RelevanceBudget.compute(intention, channels, totalTokens)` fait les deux
(pondérer + tronquer) en un passage : similarité cosine/naive → softmax
(exp(score*5)) → allocation tokens → min 5%/100 → renormalisation →
`content.take(budget * 4)`. `ChannelBudget` ne sait que tronquer. Les deux
sont des budgets token — `RelevanceBudget` est strictement plus général.

== Décisions architecturales

. *Portée EPIC* : faire consommer `RelevanceBudget` (agent-contracts 0.0.3
  déjà publié) par planner en remplaçant le budget fixe `ChannelBudget`
  par un budget dynamique dans `DecomposeIntentionTask`. Le budget
  dynamique prend l'intention + les contenus canaux et tronque selon la
  similarité.

. *Backward compat* : `ChannelBudget` reste pour les consommateurs sans
  pondération (tests, autres boroughs). `RelevanceBudget` est un upgrade
  optionnel — si l'intention est vide ou les embeddings indisponibles,
  fallback sur le contenu original (comportement actuel préservé).

. *Dépendance cross-borough BOM* : aucune nouvelle publication —
  `agent-contracts` 0.0.3 est déjà dans le classpath de planner
  (`build.gradle.kts:29`). Zéro bump BOM. `RelevanceBudget` est déjà
  disponible.

. *Dépendance cross-borough codebase* : HORS SCOPE. `CompositeContextBuilder`
  et `MultiChannelContextGraph` bénéficieront de `RelevanceBudget` dans un
  EPIC futur codebase. Borough Queens DORMANT — on ne touche pas.

. *Adapter pattern* : `RelevanceBudget.compute` prend `Map<String, String>`
  (nom canal → contenu) + `intention: String`. Planner a 4 canaux nommés
  (`eagerContext`, `ragContext`, `graphifyContext`, `docsContext`). Nouveau
  `BudgetAdapter` (object pur, domaine `planning.budget`) qui mappe
  4 canaux planner → Map → `compute` → `ChannelScore` → 4 String tronquées.

. *Fallback sécurité* : si `RelevanceBudget.compute` retourne vide ou lance,
  `BudgetAdapter` retourne les contenus originaux non tronqués (backward
  compat — le LLM reçoit le même contexte qu'aujourd'hui).

. *Non-régression critique* : `PlannerIntegration.kt` (codebase) appelle
  `IntentionPlanner.plan(eagerContext, ragContext, ...)`. Le contrat d'appel
  est inchangé — planner reçoit toujours 4 String. Seul le contenu tronqué
  change (dynamique au lieu de fixe).

. *Testabilité* : `RelevanceBudget.compute` est pure (aucun effet de bord).
  `BudgetAdapter` est pur aussi. Tests unit + functional + Cucumber BDD.

. *Méthode* : baby-step DDD/TDD/BDD, 3 niveaux tests/US
  (unit → functional → cucumber), English only code/Gherkin.

. *Ordre* :
  * US-0 cadrage (cette session)
  * US-1 `BudgetAdapter` (domaine `planning.budget`, object pur) — indépendant
  * US-2 wiring `DecomposeIntentionTask`
  * US-3 Cucumber BDD `planner_budget.feature`
