== Tentative

`NoSuchMethodError: contracts.vibecoding.registry.ToolRegistry.<init>(Map, List, int, DefaultConstructorMarker)`
à `ToolCatalog.<clinit>`.

=== Cause racine (cross-borough)

`codebase-plugin:0.0.17` (Central) **embarque** dans son JAR les classes
`contracts.vibecoding.registry.*` d'une version **plus récente** du contrat
(constructeur à 4 paramètres, `registerHandler`, `MAX_WRITE_CHARS`) :

[source]
----
$ unzip -l codebase-plugin-0.0.17.jar | grep contracts/vibecoding
contracts/vibecoding/registry/ToolRegistry.class   (API 4 paramètres)
...
----

Or `vibecoding-contracts:0.0.1` (Central) est l'API **2 paramètres**. Selon
l'ordre du classpath, le planner compile contre l'une et s'exécute contre
l'autre → `NoSuchMethodError`. Les tentatives `excludeGroup` + `PREFER_SETTINGS`
ne corrigent pas le shade embarqué dans le JAR N1.

**Verdict** : le correctif propre est **côté codebase** (ne pas empaqueter
`contracts.vibecoding` dans `codebase-plugin`, ou publier
`vibecoding-contracts:0.0.2` avec l'US courante) puis re-pin planner. Un
workaround par réflexion serait un faux vert qui masquerait le shading.
