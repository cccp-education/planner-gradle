== 2. Findings

=== 2.1 P1-1 — `Metadata.kt` orphelin : le planner ne matérialise RIEN sur disque

*Constat* : `planning/Metadata.kt` (35 lignes, contrat format pivot
`metadata.json` conforme TAXONOMIE_WORKSPACE §Format Pivot) est défini mais
*aucun usage* dans `main/`. La tâche `generatePlan` n'a aucun `@OutputFile` :
le plan part en stdout pur (`StdoutFormatter` `[PLAN]/[EPIC]/[US]/[TASK]`),
jamais persisté.

*Preuve* :
- `grep -rn "Metadata" planner-plugin/src/main/kotlin/` → uniquement `Metadata.kt` lui-même.
- `DecomposeIntentionTask.kt` : `@DisableCachingByDefault`, aucun `@OutputFile`.

*Impact vs vision* : c'est le gap majeur. La vision (TAXONOMIE_WORKSPACE,
runtime agentique, dashboard ALGER, cockpit Long Island) exige des artefacts
matériels + métadonnées pivot consommables par les N3/N4 (runner, pilot,
workspace). Aujourd'hui rien n'est exploitable hors stdout texte non parsable
(les titres `title="..."` avec guillemets internes cassent le parsing).

=== 2.2 P1-2 — Split-brain #2 non réellement clos : ToolCatalog copie manuelle alors que vibecoding-contracts EST publié

*Constat* : `ToolCatalog.kt:9-11` affirme *"Le planner ne dépend pas
directement de vibecoding-contracts (non publié proprement)"* — faux :
`repo1.maven.org/education/cccp/vibecoding-contracts` répond HTTP 200. La
décision PLN-CONTRACTS-3 (S-061) était "dépend seulement de vibecoding-contracts
(déjà publié) + adapter".

*Preuve de drift déjà effective* :
- planner : `exec_shell` → `"Execute a shell command via bash -c (DANGEROUS commands blocked)"`
- N0 `ToolRegistry.kt:48` : `"Execute a shell command via bash -c. Returns EXIT code + stdout (max 8000 chars). DANGEROUS commands blocked."`

*Impact* : l'"alignement manuel anti-drift" produit exactement la drift qu'il
prétend éviter. Si codebase ajoute un outil (ex. `list_tasks`), le prompt
planner restera muet — le LLM ne saura pas le planifier.

=== 2.3 P1-3 — La surcharge lifecycle US-2 est orpheline côté production

*Constat* : `DecomposeIntentionTask.kt:122-143` : quand
`-Pagent.lifecycle=true`, la tâche génère le plan via la surcharge
**multi-canal**, puis fait un **post-wrap** `LifecycleAdapter.toPlanned` — elle
n'appelle *jamais* la surcharge `IntentionPlanner.plan(state: AgentState.ContextReady, ...)`
livrée en US-2 (testée uniquement par `IntentionPlannerLifecycleTest`).

*Impact* : logique de wrapping dupliquée (dans la surcharge ET dans la tâche),
deux chemins lifecycle possibles dont un seul est validé par les 5 unit tests.
Le chemin réellement exercé en production n'est pas celui qui a été testé.

=== 2.4 P2-1 — Version koog en retard + dépendance directe inutilisée

*Constat* : `libs.versions.toml` : `koog = "0.8.0"` alors que slider/capsule
sont sur `koog-agents:1.0.0` (S-062/063). Et `implementation(libs.koog.agents)`
n'est importé *nulle part* dans `main/` — les seuls imports `codebase.koog.*`
viennent de codebase-plugin (N1).

*Impact* : risque de résolution transitive incohérente (koog 0.8.0 vs 1.0.0
selon le graphe) + dépendance morte. Bump à 1.0.0 (alignement BOM) ou
suppression de la dépendance directe.

=== 2.5 P2-2 — Flag `agent.lifecycle` implicite, hors extension, hors inputs

*Constat* : ni `PlannerExtension` (3 Property : intention, specsDir,
aiProvider) ni le plugin n'exposent le flag — lu en dur dans la tâche via
`gradleProperty("agent.lifecycle")`. Conséquences :
- non documenté dans `task.description` (qui mentionne seulement `-PspecsDir`) ;
- non participant aux inputs → la tâche peut être UP-TO-DATE à tort si le flag
  change (`@DisableCachingByDefault` ne désactive pas l'up-to-date checking).

=== 2.6 P2-3 — English-only violé dans le code de production

*Constat* : 4 fichiers `main/` contiennent des commentaires français :
`DecomposeIntentionTask.kt` ("EPIC 3 — Multi-Canal Convergent : task câblée…"),
`PlanningPlugin.kt` ("vibecode task supprimee…", "La tache vibecode…"),
`ToolCatalog.kt` ("alignés manuellement pour éviter la drift…"),
`IntentionPlanner.kt` (6 occurrences). Violation de la règle transverbe
English only (code/comments/Gherkin) applicable aux boroughs OSS.

=== 2.7 P3-1 — `PlannerIntegration` (codebase) contourne le hub planner

*Constat* : `codebase.rag.PlannerIntegration.kt` résout son propre provider
(`LlmServiceResolver` + env `OLLAMA_MODEL`) au lieu de consommer
`PlanningLlmService` — cohérent avec le scope DORMANT codebase, mais le pont
N1→N2 n'utilise pas le hub qu'il a lui-même motivé (S-072).

*Action* : à noter dans le backlog codebase (EPIC futur, borough DORMANT).

=== 2.8 P3-2 — Noms de tâches cross-borough hardcodés dans le prompt

*Constat* : `ToolCatalog.toPromptSection()` : `:slider:generateSlides`,
`:capsule:extractSpeakerNotes`, `:bakery:publishSite`, `:plantuml:generateDiagram`.

*Impact* : dérive silencieuse si renommés (cas réel : SLD-11 a renommé
`generateCapsule` → `extractSpeakerNotes`). Un futur `BoroughDef` (pilot-gradle,
Jersey City) devrait alimenter cette connaissance.

=== 2.9 P3-3 — 4 surcharges `plan` = plumbing fragile

*Constat* : 5-param / 8-param / 9-param / 5-param lifecycle. Le bug masqué par
cache Gradle découvert en S-076 (variables undefined dans la surcharge sans
logger) est symptomatique.

*Action* : un `PlanRequest` data class param (avec builder) serait plus sûr et
plus testable — à considérer au prochain ajout de paramètre.
